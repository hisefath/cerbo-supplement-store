2. **Role-change lock — correct, one gap in proof (R3), one strength nit (R2).** `staff-access.ts:93-99` locks the target and every finance lead in one `ORDER BY id … FOR UPDATE` statement (PostgreSQL applies the row lock after the sort, so a stable id order: no deadlock between two changes). The last-finance-lead count is taken from the locked set (:102), so two removals of different finance leads serialize and the second sees zero others (422). Refused attempts: `assertCanChangeRole` failure inserts an `outcome: 'refused'` row in its own autocommit statement before rethrowing (:83-88), as BE-18 says; 404, 409 and 422 are not logged, as the LLD order of checks says. Note: AT-029 does exercise the target-row lock (without it both requests would answer 200 and log two granted rows); what no test exercises is the multi-finance-lead path.
