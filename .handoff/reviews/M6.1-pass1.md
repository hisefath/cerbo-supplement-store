No security findings. Checked:
- Authorization: EP-42 runs `requireViewer`, then `assertRole(['patient'])`, so a provider or staff member gets 403 and a stranger 401.
- Isolation, two layers: the SQL filters `where patient_id = viewer.userId`, and each row goes through `getOrderForViewer`, which runs `assertCanViewOrder` (patient and userId match) before any write.
- Cursors cannot widen the scope. A cursor only bounds `(sent_at, id)` inside her own filter. Its values are bound parameters, and the key passes BE-22's regex and round-trip check, so input cannot reach the SQL text.
- Open redirect: ROLE_PAGES has a fixed `/orders` path. The page's own redirect goes to the fixed `/sign-in` with `next: route.fullPath`, and the guard's `safeNext` limits `next` to same-site paths. Row links are `/orders/${number}`.
- No secrets or PHI are in the tests, which use seeded test people only.

No other correctness findings. Checked:
- Totals: each list total comes from the same `getOrderForViewer` call EP-21 makes, so it always matches the order page (AT-005 shows this for a moved price).
- Keyset ordering: the ORDER BY matches the cursor's row comparison. The cursor key is UTC to the microsecond (`to_char … US"+00"`), and `sent_at` is `not null`.
- Paging: the page fetches `n+1` rows to decide on `next_cursor`. "Show 25 more" ignores a page that arrives after a reload (`gen`), and a key cannot repeat across pages.
- Bad input: an array cursor or limit is 422.
